## 1. Рішення щодо термометра: нова таблиця, а не `ALTER TABLE`

| Варіант | + | − | Вердикт |
|---|---|---|---|
| A. Колонки `goal_amount/collected_amount` у `fundraisings` + ручний `ALTER` | Простий запит | `create_all` не додасть (F1); на Postgres треба ручний SQL, на SQLite `ADD COLUMN` без `IF NOT EXISTS`; два шляхи міграції, легко розсинхронізувати dev/prod | Ні |
| B. Стартова «міграція» в коді (inspector + `ALTER`) | Автоматично | Самописний мігратор = борг; діалектні відмінності | Ні |
| C. Додати Alembic | Правильно в довгу | Нова залежність і процес, перебір для 1 колонки; «правило трьох» ще не спрацювало | Пізніше, коли знадобиться 3-тя міграція |
| **D. Нова таблиця `fundraising_progress` 1:1** | **Працює через `create_all` на обох СУБД, нуль ризику для наявних даних, відкат = `DROP TABLE`, відсутність рядка = «ціль не задано»** | Додатковий join/selectinload | **Обираю** |

Обґрунтування: єдиний спосіб, що однаково й безпечно виконується на SQLite і Postgres без нової інфраструктури. Join на 1:1 по PK-індексу дешевий. Умова: **жодних змін колонок наявних таблиць у v2** — тільки нові таблиці.

## 2. Модель даних (лише нові таблиці)

Усі успадковують `BaseMixin` (created_at/updated_at/deleted_at/created_by/updated_by), як решта.

### `fundraising_progress` (1:1 до `fundraisings`)
| Колонка | Тип | Обмеження |
|---|---|---|
| id | Integer PK | |
| fundraising_id | Integer FK `fundraisings.id` | **UNIQUE**, NOT NULL |
| goal_amount | BigInteger | NOT NULL, CHECK `> 0` |
| collected_amount | BigInteger | NOT NULL, default 0, CHECK `>= 0` |
| currency | String(3) | default `'UAH'` |
Суми — цілі гривні (без копійок і float: нема округлень, UI не вдає точності, якої не має).
Зв'язок: `Fundraisings.progress = relationship(..., uselist=False)`. Це додає **relationship** в модель, не колонку — `create_all` не зачіпає.

### `contributions` (самозвіт «Я задонатив(ла)»)
| Колонка | Тип | Обмеження |
|---|---|---|
| id | Integer PK | |
| user_id | Integer FK `users.id` | NOT NULL, index |
| fundraising_id | Integer FK `fundraisings.id` | NOT NULL |
| period | String(7) | `YYYY-MM`, CHECK формату, NOT NULL |
**UNIQUE(user_id, fundraising_id, period)** — ідемпотентність. `created_at` з міксина = час натискання.
Чесність: це **не** підтверджений платіж. Суми не зберігаємо взагалі (її ми не знаємо; поле створило б ілюзію точності).

### Зміни у `subscriptions` (B5) — без нових колонок
- Дані: одноразовий скрипт-дедуплікація (залишити найменший `id` на пару `(user_id, fundraising_id)`; якщо є активний — він, інакше найновіший soft-deleted), решту видалити фізично.
- Унікальність: `UniqueConstraint(user_id, fundraising_id)` у моделі **не з'явиться на наявній таблиці через `create_all`** (F1). Тому гарантія дворівнева: (1) логіка «upsert/реактивація» у `crud` (див. §3.5); (2) `CREATE UNIQUE INDEX IF NOT EXISTS ux_subscriptions_user_fundraising ON subscriptions(user_id, fundraising_id)` — синтаксис однаково валідний у SQLite і Postgres, виконується разом зі скриптом дедуплікації (`server/scripts/dedupe_subscriptions.sql`, запуск вручну один раз, ідемпотентний). Модель теж оголошує constraint, щоб нові/тестові БД мали його з коробки.

## 3. API-контракти

Спільні правила для **нових** ендпоінтів:
- Автентифікація: нова залежність `get_current_user(request, db)` сама декодує куку `access_token` (не покладається на `request.state.user`, див. F3) → `Users` або 401/403. Шляхи `/contributions*` **не** додаються в `open_paths`; `/fundraisings/{id}/progress` вже під відкритим префіксом, тому захист робить саме залежність, а не middleware.
- Ідентичність береться з токена. `user_id`/`creator_id` у тілі нових ендпоінтів **відсутні**.
- Помилки — стандартний FastAPI `{"detail": "..."}`.
- Час: «поточний період» рахується на сервері в `Europe/Kyiv` (`zoneinfo`), клієнту довіряти не можна.

### 3.1 Термометр
| | |
|---|---|
| `PUT /fundraisings/{id}/progress` | Створити/замінити ціль і зібране (upsert). Лише власник збору. |
| Авторизація | кука обов'язкова; `current_user.id == fundraising.creator_id`, інакше 403 |
| Тіло | `{"goal_amount": 100000, "collected_amount": 42000}` (`currency` необов'язково, лише `"UAH"` у v2) |
| 200 | `{"goal_amount","collected_amount","currency","percent": 42,"updated_at"}` |
| Помилки | 401/403 без куки / не власник; 404 збору нема або `deleted_at`; 422 `goal_amount<=0`, `collected_amount<0`, нецілі, > 10^12 |
| Примітки | `collected > goal` дозволено (UI обмежує смугу 100 %); `percent` рахує сервер (`min(100, round(100*c/g))`). `DELETE` того ж шляху — прибрати термометр (soft delete), 204. |

Читання: поле `progress` у відповідях **наявних** `GET /fundraisings/`, `GET /fundraisings/{id}`, `/by-creator/…`, `/by-organization/…`:
`"progress": null | {"goal_amount","collected_amount","currency","percent","updated_at"}` — адитивна зміна, старі клієнти не ламаються. UI **зобов'язаний** показувати «оновлено {updated_at}» (чесність: дані ручні).

### 3.2 Кількість підписників
Поле `subscribers_count: int` (≥ 0) у тих самих відповідях `Fundraisings`. Рахується як `COUNT(DISTINCT user_id)` по `subscriptions` з `deleted_at IS NULL`. Для списків — **одним** `GROUP BY fundraising_id` запитом на сторінку (не N+1), результат докладається в `crud`. Кеш не потрібен (≤100 рядків за сторінку). Жодних ПІБ/email — лише число.

### 3.3 Contributions
| Метод/шлях | Призначення | Авторизація | Тіло | Відповідь | Помилки |
|---|---|---|---|---|---|
| `POST /contributions` | Позначити «я задонатив(ла)» у поточному місяці | кука | `{"fundraising_id": 7}` | 201 `{"fundraising_id":7,"period":"2026-10","created":true,"stats":{…}}`; повтор у тому ж місяці → **200** з `created:false` (ідемпотентно) | 401/403 без куки; 404 збору нема; 422 некоректний id |
| `DELETE /contributions/{fundraising_id}` | Скасувати позначку **поточного** місяця (помилковий клік) | кука | — | 200 `{"stats":{…}}` (також якщо нічого скасовувати — ідемпотентно) | 401/403 |
| `GET /contributions/me` | Серія й історія | кука | — | `stats` (нижче) | 401/403 |

`stats`:
```
{
  "current_month": "2026-10",
  "current_month_done": true,
  "streak": 3,            // поспіль місяців, див. правило нижче
  "best_streak": 5,
  "total_months": 9,      // кількість місяців з ≥1 внеском
  "last_12": [{"period":"2026-10","count":2}, ...],   // у зростаючому порядку, без пропусків (count:0)
  "by_fundraising": [{"fundraising_id":7,"months":4}]
}
```
Правила (узгоджено з Sally — «без покарання за пропуск»):
- Місяць зараховано, якщо є ≥1 `contributions` (будь-який збір).
- `streak` = довжина безперервного ланцюга місяців, що закінчується **поточним, а якщо поточний ще порожній — попереднім** (поточний місяць не «ламає» серію, поки він триває). Пропущений повний місяць обнуляє `streak`, але `best_streak` і `total_months` лишаються.
- Підписка на збір для внеску **не обов'язкова** (можна донатити разово).
- Заборонено: вказувати довільний `period`, чужого користувача, майбутні місяці. Бекдейт у v2 не підтримуємо (інакше це дірка для накрутки навіть самозвіту).

### 3.4 Публічна лічба внесків (опційно, не обов'язково для v2)
`contributions_this_month` у `Fundraisings` — **не робимо**: це публічний показник на основі самозвіту, який можна накрутити й який виглядає як зібрані кошти. Термометр — єдиний «прогрес зборів», і він явно ручний.

### 3.5 Підписки (B5)
| Зміна | Поведінка |
|---|---|
| `POST /subscriptions/` | Ідемпотентний upsert: активна пара → 200 з наявним рядком; soft-deleted пара → `deleted_at = NULL` (реактивація) і 200; нема → INSERT, 201. Тіло/відповідь без змін (`SubscriptionsCreate`/`Subscriptions`) — клієнт не ламається. Додатково: 404 якщо `fundraising` нема. Гонка двох POST: другий ловить `IntegrityError` на унікальному індексі → повторне читання → 200. |
| `DELETE /subscriptions/{u}/{f}` | Виправити F7: `soft_remove_subscription` повертає оновлений рядок; 404 лише коли активної підписки реально нема. **Перед правкою звірити клієнт** (`services/api` — як обробляється 404). |
| Ідентичність | На етапі B5 `user_id` ще з тіла (не ламаємо контракт). Звірка з токеном — у блоці безпеки (§5, R2). |

### 3.6 Виправлення B1 (CORS)
Змінити лише порядок/склад middleware: `CORSMiddleware` додати **останнім** (стане зовнішнім), прибрати гілку `if request.url.path == "/me"` в `AuthMiddleware` (роут сам повертає 403/404). Очікуваний результат: гість отримує 403 **із** `Access-Control-Allow-Origin`; клієнт обробляє його як «не залогінений» без червоної плашки (клієнтська частина — Amelia: не показувати помилку для `/me` 403). Заодно: усі відповіді-помилки middleware (403 на закритих шляхах) теж стануть CORS-видимими — це бажано.

### 3.7 Виправлення B4
Бекенд: нічого, окрім нових полів (F6). Клієнт: сторінка збору завжди робить `GET /fundraisings/{id}` за `:id` з URL, `location.state` — лише для миттєвого показу. Потребує маршруту з параметром (`/fundraising/:id`) — це зміна `appRoutes.tsx`, дозволена за рішенням Андрія №2.

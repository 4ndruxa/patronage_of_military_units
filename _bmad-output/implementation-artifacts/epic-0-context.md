## Goal

Привести проєкт до відтворюваного «зеленого» стану перед будь-якими змінами поведінки чи редизайном: клієнтські тести (jest) і перевірка типів проходять, бекенд-тести (pytest) запускаються й стабільно проходять, а вигляд сайту «до» зафіксовано скріншотами. Це точка відліку, відносно якої перевіряється кожен наступний епік (баги й безпека, потім редизайн). Епік не змінює поведінку застосунку.

## Stories

- Story 0.1: Зелений jest (синхронізація lock-файлу, `jest-util`)
- Story 0.2: Зелений pytest (запуск з кореня, `test.db` в `.gitignore`)
- Story 0.3: Скріншоти «до» (відкладено користувачем; поточна робота охоплює лише 0.1 і 0.2)

## Requirements & Constraints

- Клієнт: `npm ci` проходить на чистому `node_modules`; `npx jest` — 3 сьюти зелені; `npx tsc --noEmit` — 0 помилок.
- Коміт для 0.1 містить лише файли пакетів (`package.json`, `package-lock.json`), без інших змін.
- Бекенд: 10 з 10 тестів зелені на чистому середовищі, повторний запуск поспіль також зелений (ізоляція БД між запусками).
- `server/test.db` не має потрапляти в git (додати в `.gitignore`).
- Скріншоти (0.3): усі сторінки, ширини 1366 і 390 px, у `screenshots/before/` поруч із планом.
- Жодних змін логіки, розмітки чи схеми БД; кожен крок закінчується окремим комітом; `tsc`, `jest`, `pytest` мають лишатися зеленими.

## Technical Decisions

- Причина падіння jest: lock-файл не знає про `jest`/`ts-jest`, а `ts-jest` вимагає `jest-util` з кореня `node_modules` (peer-залежність). Рішення: `npm i -D jest-util@^29.7.0` у `patronage-client`.
- `jest.config.js` (середовище `node`, лише `*.test.ts`, застарілий `globals['ts-jest']`) для сервісних тестів працює; не чіпати в цьому епіку (компонентні тести — Е1, задача 1.8).
- Pytest: тести імпортують `server.sql_app...` та `server.main`, тому запуск лише з кореня репозиторію (`python -m pytest server/test_main.py`) у свіжому venv зі `server/requirements.txt` (`pytest-asyncio`, `httpx` уже там). Закомічений `server/virtualenv` не використовувати.
- Docker: код монтується як `./` (тобто `server/`) у `/app`, пакета `server` там нема. Обране рішення без зміни коду: `docker compose run --rm -v $(pwd)/..:/repo -w /repo backend python -m pytest server/test_main.py`.
- Непідтверджений ризик: подвійний імпорт моделей під різними іменами модулів (`server.sql_app.models` vs `sql_app.models`) може дати «Table already defined». З'ясувати першим кроком 0.2; якщо підтвердиться — додати корінь і `server/` у `PYTHONPATH` та змінити імпорти в тестах на `sql_app...`/`main`.
- Тести пишуть у `./test.db`; перевірити, що повторний запуск не залежить від залишків попереднього.

## Cross-Story Dependencies

- Е0 — перший за суворим порядком; Е1 (баги B1–B5, безпека) і всі наступні епіки спираються на зелений baseline, зокрема нові pytest-тести (спершу червоні) потребують працюючого запуску з 0.2.
- Скріншоти 0.3 мають бути зроблені до будь-яких візуальних змін (Е2+) — інакше «до» втрачається; зараз відкладено, тож це треба зробити до початку Е2.
- 0.1 і 0.2 незалежні одна від одної (клієнт і сервер).
